# CLI

Somatic's CLI is a minimal local scaffold runner implemented with Python's standard library.

It does not install dependencies, call external APIs, use provider secrets, access the network, run real lab systems, run biomodels, execute Fabric transport, or access live sensors.

## Run a Fixture Workflow

```powershell
python -m somatic run fixtures/workflows/valid-literature-only.yaml
```

Optional deterministic run id:

```powershell
python -m somatic run fixtures/workflows/valid-literature-only.yaml --run-id run-local-demo
```

Optional output directory:

```powershell
python -m somatic run fixtures/workflows/valid-literature-only.yaml --runs-dir runs
```

When installed, the console script is:

```powershell
somatic run fixtures/workflows/valid-literature-only.yaml
```

## Doctor

```powershell
python -m somatic doctor
```

Reports the local scaffold status, including that the basic runner is offline and requires no provider secrets.

## Local UI

```powershell
python -m somatic ui
python -m somatic ui --no-browser --port 8765
```

Starts a stdlib HTTP server bound to **127.0.0.1** and opens the graphical app. Nothing leaves the machine. `--host` must be loopback (`127.0.0.1` or `localhost`). See `docs/how-it-works/local-ui.md`.

## Consent

```powershell
python -m somatic consent status
python -m somatic consent grant analysis-insight
python -m somatic consent revoke analysis-insight
python -m somatic consent erase
```

Persists grants in local JSON (`~/.somatic/consent.json`, or `SOMATIC_CONSENT_PATH`) with owner-only permissions. Every scope defaults OFF. Missing or invalid files load as all-OFF. `erase` calls the right-to-erasure hook and deletes the file. `analyze` / `share` `--grant` still works as a session overlay and does not write the store.

Doctor also summarizes the sanitized sensor-evidence provider registry by
provider ID, provider count, validation status, and metadata-only boundary. It
does not print fixture refs, fixture bodies, workflow private values, or
provider/parser payload bodies. Where `document-fixture` appears, doctor also
prints the sanitized metadata-only adapter boundary and confirms ingestion,
parsing, and network paths remain disabled. Where `wifi-csi` appears, doctor
also prints the sanitized metadata-only CSI source boundary, conditional RuView
reference status, and booth-first profile while confirming RuView execution,
device flashing, model use, capture, monitor mode, and network paths remain
disabled.
Doctor also reports compact Phase 11B review-record status, Phase 11C
preflight dossier status, Phase 11D lifecycle audit status, Phase 11E
audit-index/change-control status, Phase 11F audit handoff status, and
Phase 11G handoff acceptance status, and Phase 11H follow-up/remediation
status, Phase 11I follow-up queue-index status, Phase 11J decision closeout
status, Phase 11K review-trail export status, Phase 11L runtime gap ledger
status, and Phase 11M planning/governance closeout status for document and
WiFi CSI planning surfaces. It prints status, decision, and count metadata only; it does
not dump
review-record fixture bodies, dossier bodies, lifecycle record bodies,
audit-index bodies, change-control bodies, handoff input records, acceptance
input records, follow-up source records, queue bodies, closeout source records,
review-trail bodies, runtime gap ledger source bodies, governance closeout
source bodies, or permit runtime execution.

## Sensor Evidence Provider Discovery

```powershell
python -m somatic sensor-evidence providers
python -m somatic sensor-evidence providers --format json
```

Lists registered fixture-only sensor-evidence providers from the Phase 10D
provider manifest generated by `somatic.sensors.registry`. The command is
read-only and prints sanitized metadata only:

- `provider_id`
- `provider_kind`
- `evidence_kind`
- `contract_version`, `contract_identity`, and manifest contract version
- `artifact_name`
- fixture-only status
- fixture mode labels
- supported fixture formats
- public artifact-boundary label
- adapter boundary labels when the provider has an adapter boundary
- compact review-record status when the provider has a Phase 11B planning surface
- compact preflight dossier status when the provider has a Phase 11C planning surface
- compact lifecycle audit status when the provider has a Phase 11D planning surface
- compact audit-index/change-control status when the provider has a Phase 11E planning surface
- compact audit handoff status when the provider has a Phase 11F planning surface
- compact handoff acceptance status when the provider has a Phase 11G planning surface
- compact follow-up/remediation status when the provider has a Phase 11H planning surface
- compact follow-up queue status when the provider has a Phase 11I planning surface
- compact decision-closeout status when the provider has a Phase 11J planning surface
- compact review-trail export status when the provider has a Phase 11K planning surface
- compact runtime gap ledger status when the provider has a Phase 11L planning surface
- compact planning/governance closeout status when the provider has a Phase 11M planning surface

JSON output is the machine-readable manifest snapshot contract. It includes
`manifest_contract_version`, `manifest_kind`, stable `provider_order`,
`provider_count`, and the provider list. Keep
`fixtures/providers/sensor-evidence-provider-manifest-v1.json` in sync when a
registry metadata change is intentional.

The command does not read fixture bodies, instantiate providers, create run
artifacts, call networks, export raw values, print fixture refs, or embed
provider/parser internals. Exit code is `0` when the registry loads; CLI usage
errors use argparse's standard `2`.

## Sensor Evidence Workflow Validation

```powershell
python -m somatic sensor-evidence validate --workflow fixtures/workflows/valid-n-of-1.yaml
python -m somatic sensor-evidence validate --workflow examples/sensor-evidence-demo/toy-counter-fixture-workflow.yaml --format json
```

Validates only the sensor-evidence provider config embedded in a local workflow
YAML. It returns `0` when the sensor-evidence config is valid and `1` when it
fails closed. JSON output mirrors the sanitized registry validation result and
adds `schema_version`.

Validation errors are category-coded without echoing rejected refs, paths, URLs,
provider IDs, fixture names, credentials, or private scalar values. Current
categories include:

- `unknown_provider`
- `unsafe_ref`
- `excessive_count`
- `live_device_network_field`
- `credential_like_field`
- `unsupported_fixture_mode`
- `unsupported_fixture_format`
- `offline_boundary_flag`
- `private_scalar`

The validation command does not generate run artifacts and does not change
evidence-pack behavior, fingerprints, rankings, Elo, brackets, winners, Fabric
refs, or public examples.

## Sensor Evidence Artifact Inspection

```powershell
python -m somatic sensor-evidence inspect --artifact runs/example/artifacts/document_evidence_pack.json
python -m somatic sensor-evidence inspect --artifact runs/example/artifacts/document_evidence_pack.json --format json
```

Inspects a persisted sanitized document evidence-pack artifact and reports
compatibility, provider/evidence kind, artifact name, run-relative artifact ref,
status, readiness status, pack fingerprint, count summary, and sanitized score
metadata. For document evidence packs it also reports sanitized adapter status,
adapter boundary labels, adapter output-validation status, and the shared
real-mode readiness gate status.

The command is a local metadata check only. It does not parse source documents,
call networks, ingest external documents, instantiate live providers, expose the
supplied local path, print fixture filenames, print document text, print URLs,
print source identifiers, or export provider/parser bodies. Unsupported artifact
kinds fail closed with sanitized errors.

Provider discovery and `doctor` also surface the shared real-mode readiness
gate for adapter-backed providers. Current adapters report
`blocked-fixture-reference-only`, list the missing gate count, and keep
execution disabled.

Phase 10I uses these provider discovery, doctor, workflow report, and artifact
inspection surfaces as shared safety-invariant checkpoints for document and
WiFi CSI evidence. The CLI remains metadata-only and does not enable real
runtime behavior.

## Launch

```powershell
python -m somatic launch --config path/to/config.yaml
```

Loads a local YAML launch plan and reports that advanced lanes are disabled unless explicitly configured. Phase 1C does not execute advanced lanes.

## Replay

```powershell
python -m somatic replay run-id
```

If `runs/{run-id}/manifest.json` exists, Somatic prints the manifest. Commit replay is scaffolded for future work but is not implemented in Phase 1C.

## WiFi CSI Fixture Parse

```powershell
python -m somatic csi-parse sample-esp32-csi.csv --repo-root .
```

Parses one local fixture under `fixtures/sensors/csi/` and prints sanitized
aggregate report/summary metadata. This is the same offline parser contract used
by the Phase 8D sandbox provider replay path. The JSON includes Phase 8E
`csi_evidence_scoring` metadata computed from sanitized counts and statuses
only. The command does not perform live capture, serial, MQTT, UDP, pcap,
monitor mode, hardware access, network calls, vital-sign inference, diagnosis,
treatment, monitoring, or emergency triage.

Public CSI example manifests live under `examples/wifi-csi-demo/`. They point
at the existing CLI and workflow fixtures:

```powershell
python -m somatic csi-parse sample-esp32-csi.csv --repo-root .
python -m somatic csi-parse mixed-valid-invalid-csi.csv --repo-root .
python -m somatic csi-parse unsupported-csi.npz --repo-root .
python -m somatic run fixtures/workflows/valid-n-of-1.yaml --runs-dir runs/examples --run-id run-csi-n-of-1-example
python -m somatic run fixtures/workflows/valid-hypothesis-tournament.yaml --runs-dir runs/examples --run-id run-csi-tournament-example
```

Run these commands from the repository root so local fixture refs and
`runs/examples` resolve inside the clone. See
`docs/wifi-csi-public-examples.md` for the quick verification path and
release-readiness checklist.

## Fabric Check

```powershell
python -m somatic fabric check fixtures/fabric/conformance/sample-pack-signed.json
```

Validates a local pack, keyring, or catalog JSON file. This is a local shape/precheck command only; it does not fetch, seed, install, enable, or execute packs.

With the optional Fabric crypto backend available, pass a local keyring to verify a signed pack manifest against the trusted publisher threshold:

```powershell
python -m somatic fabric check fixtures/fabric/crypto/signed-code-pack.json --keyring fixtures/fabric/crypto/keyring-signed.json
```

If `--keyring` is used without the optional crypto backend, the command fails closed. The crypto fixtures are deterministic test vectors and include test-only private keys that must never be used for real publishing.

## Behavior

The `run` command:

- Loads a workflow YAML fixture with a conservative internal parser.
- Validates required top-level fields from `docs/workflow-schema.md`.
- Loads local mock provider metadata from `fixtures/providers/`.
- Attaches `fixtures/evidence/sample-evidence-record.json`.
- Attaches `fixtures/safety/sample-safety-response.json`.
- Generates three placeholder hypotheses.
- Writes a Markdown report.
- Writes `runs/{run_id}/` artifacts.

## Output Boundary

Generated reports are mock/offline, research-only, and not medical advice. They are not real provider, lab, biomodel, Fabric, sensor, or clinical outputs.
